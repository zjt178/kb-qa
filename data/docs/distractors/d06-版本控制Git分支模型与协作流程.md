# 版本控制 Git 分支模型与协作流程

## 概述

Git 是分布式版本控制系统，每次克隆都包含完整历史。理解提交对象、分支指针和合并方式，是团队协作不打架的前提。本文梳理对象模型、常见分支策略和冲突处理思路。

## 对象模型

Git 的核心对象有三类。blob 存文件内容，tree 存目录结构，commit 指向一棵 tree 并记录父提交、作者和时间。分支本质上只是一个指向某个提交的可移动指针。

这个模型解释了几个常见困惑：为什么切换分支如此快——只改了一个指针；为什么提交后原始内容还在——旧对象没有被删除，直到触发垃圾回收。

引用日志记录了指针的移动历史，误删分支或回退过头时，可以靠它找回丢失的提交。

## 常见分支策略

**主干开发**：所有人向主分支提交，靠特性开关控制未完成功能是否对外可见。集成频繁，冲突小，但对自动化测试要求高。

**特性分支**：每个需求开一条分支，完成后合并回主干。隔离性好，但分支存活时间越长，合并冲突越严重。

**发布分支**：为每个版本拉一条发布分支用于修复，主干继续开发新功能。适合有明确版本节奏的产品。

无论选哪种，核心纪律是缩短分支寿命。分支存活时间与合并成本正相关，这条规律比具体选哪种模型更重要。

## 合并与变基

合并会生成一个合并提交，保留真实的分支拓扑，历史是网状但忠实。

变基则把当前分支的提交逐个重放到目标分支上，历史变成一条直线，阅读清爽但改写了提交身份。因此对已经推送并被他人拉取的分支做变基会造成混乱，这条约束通常概括为：只对尚未共享的本地提交做变基。

合并冲突的根源是两个分支修改了同一文件的同一区域。处理原则是先理解双方意图，再决定保留哪一方或整合，而不是机械地选一边。冲突标记只是提示，语义判断只能靠人。

## 日常实践

提交应当小而聚焦，一个提交只做一件事，便于回滚和定位。提交信息写清动机比写清改动更重要，因为改动本身看代码就知道，动机只能靠文字留存。

忽略文件配置要在项目初期就定好，把构建产物、依赖目录和本地配置排除在外，避免误提交。

## 要点清单

- 分支只是指向提交的指针，所以切换极快
- 引用日志是误操作后的救命绳
- 分支存活时间与合并成本正相关，缩短分支寿命最重要
- 变基改写提交身份，只对未共享的提交使用
- 合并保留拓扑，变基获得线性历史，各有取舍
- 提交信息要写动机，改动本身代码里可见
