# 容器与编排 Docker 与 Kubernetes 基础

## 概述

容器用命名空间做隔离、用控制组做资源限制，把应用和依赖打包成可移植的镜像。编排系统则解决多容器在集群上的调度、伸缩与自愈。本文梳理镜像分层、容器运行时原理和编排系统的核心对象。

## 镜像分层与联合文件系统

Docker 镜像由多层只读层叠加而成，每一层对应一条构建指令。容器启动时在最上面加一个可写层，所有修改都落在这一层。

分层机制带来两个收益：镜像层可以在不同镜像间共享，节省磁盘和传输；构建时未变化的层直接命中缓存，加速构建。

这也解释了 Dockerfile 的优化原则：把变化频率低的指令写前面，变化频繁的写后面，否则每次改动都会让后续所有层缓存失效。多阶段构建则用于去掉编译期依赖，只把运行时产物复制到最终镜像。

## 容器的隔离机制

容器不是轻量虚拟机，它复用宿主内核。隔离依靠命名空间：进程、网络、挂载、主机名、用户等各自独立视图。资源限制依靠控制组，对 CPU、内存、磁盘读写带宽做约束。

由于共享内核，容器逃逸的影响面比虚拟机大，因此生产环境要在权限、能力集和挂载上做收紧，避免使用特权模式。

## 编排系统的核心对象

**Pod**：最小调度单位，可包含多个共享网络命名空间的容器，通常一个主容器加若干辅助容器。

**Deployment**：管理无状态应用的副本数和滚动更新，保证期望副本数与实际一致。

**Service**：为一组 Pod 提供稳定访问入口，配合负载均衡把流量分发到健康实例。

**ConfigMap 与 Secret**：把配置和敏感信息与镜像解耦。

**探针**：存活探针失败会重启容器，就绪探针失败会把实例从流量中摘除。两者的区别很关键，混淆会导致滚动更新期间流量被导到未就绪实例。

## 资源管理与调度

调度器根据资源请求量筛选可用节点，再按打分策略选择最优节点。requests 决定调度，limits 决定运行时上限。

常见问题是不设 requests 导致节点超卖，多个实例挤在同一节点互相影响。内存超限会被直接终止，CPU 超限则只是被限流，两者的表现完全不同：前者是突然重启，后者是延迟升高。

## 要点清单

- 镜像分层实现共享与缓存，指令顺序影响构建效率
- 容器共享宿主内核，隔离靠命名空间，限额靠控制组
- 存活探针负责重启，就绪探针负责摘流量，不可混淆
- requests 影响调度，limits 影响运行，不设 requests 会超卖
- 内存超限被终止，CPU 超限被限流，故障表现不同
- 共享内核意味着逃逸风险更大，权限要收紧
