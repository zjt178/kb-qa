# 计算机网络 TCP 可靠传输机制

## 概述

TCP 通过序号、确认、重传和滑动窗口，在不可靠的 IP 网络上提供可靠传输。本文梳理三次握手、四次挥手、流量控制与拥塞控制的核心机制，以及线上服务常见的连接类故障特征。

## 三次握手与四次挥手

三次握手的目的是双方向确认彼此的收发能力和初始序号：客户端发 SYN 并携带自己的初始序号，服务端回 SYN+ACK 确认并给出自己的初始序号，客户端再回 ACK。

之所以需要三次而不是两次，是因为两次只能确认客户端到服务端的通道，服务端无法确认自己的报文能被收到，历史上重复的旧连接请求会造成服务端建立无效连接。

四次挥手是因为 TCP 是全双工的，一方发送 FIN 只表示自己不再发数据，对方仍可能继续发送。服务端收到 FIN 后先回 ACK，等自己的数据发完再发 FIN，因此比握手多一次。

## 流量控制与滑动窗口

接收方通过报文里的窗口字段告诉发送方自己还能接收多少字节，这叫流量控制。窗口为 0 时发送方停止发送，并周期性发送窗口探测报文，避免双方互相等待造成死锁。

发送方维护一个发送窗口，窗口内的数据可以连续发送而不必逐个等待确认，这就是流水线传输。窗口越大，带宽利用率越高，但对接收方缓冲要求也越高。

## 拥塞控制

拥塞控制关注的是网络整体负载，由四个阶段组成：慢启动、拥塞避免、快速重传、快速恢复。

慢启动阶段拥塞窗口从较小值开始，每收到一个确认就加倍增长，呈指数上升；达到阈值后进入拥塞避免，改为线性增长。出现丢包时，超时重传会把窗口降回起点，而收到三个重复确认则触发快速重传和快速恢复，窗口只减半，这是为了区分偶发丢包和严重拥塞。

拥塞控制算法从早期的 Reno 演进到 CUBIC，再到以 BBR 为代表的基于带宽时延积建模的算法。不同算法的差异在高丢包率的跨地域链路上表现得最明显。

## 常见故障特征

连接被拒绝通常表示目标端口没有监听进程；连接超时通常是中间链路被防火墙丢弃；连接建立后长时间无数据要区分对端进程卡死和网络丢包。排查顺序一般是先看握手是否成功，再看数据是否流动，最后定位到具体链路。

## 要点清单

- 三次握手确认双向收发能力和初始序号，两次不够
- 四次挥手源于 TCP 全双工，两个方向要分别关闭
- 滑动窗口决定流水线深度，窗口为 0 会触发探测
- 慢启动指数增长，拥塞避免线性增长
- 超时重传降窗激进，快速重传只减半，对应不同拥塞程度
- 连接被拒绝看监听，连接超时看链路
