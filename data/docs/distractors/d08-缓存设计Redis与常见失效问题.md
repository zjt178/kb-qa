# 缓存设计 Redis 与常见失效问题

## 概述

缓存通过把热点数据放在更快的存储上降低响应时间，但引入了一致性和穿透风险。本文梳理缓存更新策略、常见异常场景及其防护手段。

## 缓存更新策略

**旁路缓存**：读时先查缓存，未命中则查数据库并回填；写时先更新数据库再删除缓存。这是最常用的模式，实现简单，逻辑清晰。

为什么是删除而不是更新缓存？因为更新缓存意味着要处理并发写导致的乱序覆盖，而删除让下次读自然回填，只有一次数据库查询的代价。

**写穿**：写时同时更新数据库和缓存，一致性更好，但写入路径变长，且对冷数据做了无意义的缓存写入。

**回写**：只写缓存，定期批量落库，吞吐最高，但断电会丢数据，仅适合可容忍丢失的场景。

## 缓存穿透、击穿与雪崩

**穿透**：查询的键在数据库里也不存在，导致每次请求都打到数据库。防护手段是缓存空值并设置较短过期时间，或者用布隆过滤器提前拦截明显不存在的键。

**击穿**：某个热点键过期瞬间，大量并发请求同时穿透到数据库。防护手段是互斥锁保证只有一个请求去回源，其余等待；或者对热点键设置逻辑过期，由后台线程异步刷新。

**雪崩**：大量键同一时刻失效，或者缓存服务整体故障，导致数据库被瞬间压垮。防护手段是给过期时间加随机抖动，避免同时失效；以及做多级缓存，在本地保留一层。

三者的区别用一句话概括：穿透是键不存在，击穿是单个热点键失效，雪崩是大面积同时失效。

## 数据一致性的取舍

缓存与数据库的强一致需要分布式锁或事务协调，代价高。大多数业务选择最终一致，通过设置合理的过期时间兜底，把不一致窗口控制在可接受范围内。

一个实用判断是问业务方：读到旧数据的窗口可以有多长。如果答案是几秒，那么短过期时间加删除策略就够了，不需要引入复杂机制。

## 要点清单

- 旁路缓存最常用，写路径先更库后删缓存
- 删除而非更新缓存，避免并发写乱序覆盖
- 穿透源于键不存在，用空值缓存或布隆过滤器
- 击穿是单热点键失效，用互斥锁或逻辑过期
- 雪崩是大面积失效，用过期抖动和多级缓存
- 一致性要按业务可接受的不一致窗口来定，不必强求强一致
