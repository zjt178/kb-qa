# 17 LangChain Agent 与 Tool 调用机制

## 概述

Chain 和 Agent 的本质区别只有一句话：**Chain 是固定流程，Agent 是动态决策**。Chain 里"先检索再生成"是你写死的；Agent 里"下一步做什么"由模型自己决定。本文讲清 Agent 的运行循环、Tool 的三要素、工具调用的底层机制，以及为什么工具描述的质量决定一切。

## Chain 与 Agent 的区别

**Chain（链）**：流程由开发者预先定义。`retrieve → format → generate`，无论什么问题都走这三步。行为可预测、延迟稳定、调试容易。

**Agent（智能体）**：流程由模型在运行时决定。拿到的工具可能有"查知识库""查数据库""算数"三个，模型读完问题后自己判断该调哪个、调几次、什么时候停下来给出答案。

什么场景该用 Agent？**当"走哪条路"本身取决于问题时**。比如用户问"上个月的销售额是多少"，需要查数据库；问"我们的报销标准是什么"，需要查知识库；问"这两者冲突时以哪个为准"，需要两个都查再综合。这种分叉用 Chain 表达会变得非常臃肿（一堆 if-else），而 Agent 天然处理。

## Agent 的核心循环

Agent 的运行是一个循环，业界常称为 **ReAct**（Reasoning + Acting，推理与行动交替）：

```
思考（Thought）     —— 我需要先查一下报销标准
行动（Action）      —— 调用 search_knowledge_base，参数：报销标准
观察（Observation） —— 工具返回了一段文本
思考（Thought）     —— 内容够了，可以回答了
最终答案（Answer）  —— ...
```

循环终止条件是：模型认为信息足够，输出最终答案；或者达到步数上限（`max_iterations`）强制停止。

**这个循环的每一次迭代都是一次完整的大模型调用**，所以 Agent 的延迟和成本远高于 Chain。一个需要调用两次工具的问题，至少消耗三次模型调用（思考、再思考、终答）。

## Tool 的三要素

一个工具对模型可见的信息只有三部分：

1. **名称（name）**——模型靠它指定"我要调用哪个工具"。英文小写下划线命名是惯例，如 `query_order_status`
2. **描述（description）**——模型靠它判断"什么时候该用这个工具"。**这是最关键的部分**
3. **参数 schema**——模型靠它构造调用参数。通常用 JSON Schema 描述每个参数的类型和含义

## 为什么描述决定一切

模型选择工具**完全靠读描述**，它看不到工具的内部实现。所以：

- 描述含糊：`"查询数据"`——模型不知道查什么数据、什么时候该用，容易选错或该用的时候不用
- 描述具体：`"根据订单号查询订单的当前状态（待付款/已发货/已完成）。参数 order_id 是 12 位数字字符串"`——模型能准确判断适用场景并构造正确参数

经验法则：**写工具描述时，假设读者是一个完全不了解你系统的人**。说明这个工具做什么、什么时候用、参数是什么格式、返回什么。必要时在描述里给一个调用示例。

描述里还可以写"负面约束"，比如 `"本工具只能查单个订单，批量查询请用 query_orders_by_date"`——明确排除边界能显著降低选错工具的概率。

## 工具调用的底层机制（Function Calling）

模型本身不会执行任何代码，它做的是**输出结构化数据**。现代模型（GPT、Claude、Qwen 等）都支持 function calling（也叫 tool calling）：

1. 调用模型时，把可用工具的名称、描述、参数 schema 一起传进去
2. 模型判断需要调用工具时，输出的不是自然语言，而是一段结构化内容：`{"tool": "query_order_status", "args": {"order_id": "123456789012"}}`
3. **框架（LangChain）负责真正执行**这个工具函数，拿到返回值
4. 框架把返回值包装成一条新的消息（角色是 tool）塞回对话历史
5. 再次调用模型，模型看到工具结果后继续推理

关键点：**模型负责"决定调什么"，框架负责"实际去调"**。这个分工是理解 Agent 的钥匙。模型从来没有真正访问过数据库，它只是"说要访问"，真正访问的是你的 Python 代码。

## 常见 Agent 模式

- **ReAct**：思考-行动交替，最经典，适合工具少、任务简单的场景
- **Plan-and-Execute（先规划再执行）**：先让模型产出完整计划，再逐步执行。适合多步骤复杂任务，可以并行执行计划中的独立步骤
- **多 Agent 协作**：把不同职责拆给不同 Agent（检索 Agent、计算 Agent、审核 Agent），由一个主管 Agent 调度。适合复杂业务流，但成本和调试难度陡增
- **Reflection（反思）**：执行完让模型自己检查结果，不合格就重做。能提升质量，代价是成倍延迟

## 注意事项

- **工具数量不是越多越好**。工具超过 10 个以后，模型的选错率明显上升，因为描述之间的区分度不够。常见解法是分组，或先用一个"路由 Agent"判断该用哪一组
- **必须设 max_iterations**。否则遇到模型判断不了的情况会一直循环调用工具，烧钱且不返回结果
- **每次工具调用都是额外延迟**。如果场景是固定流程，用 Chain 不要用 Agent
- **工具报错要友好返回**。工具抛异常会让 Agent 直接崩掉；更好的做法是返回一条"调用失败，原因是 X，请换个方式"的文本，让模型有机会补救
- **参数校验要在工具内部做**。不能假设模型一定会构造出合法参数，参数缺失或格式错误时要返回明确的错误信息而不是抛异常

## 要点清单

- Chain 是固定流程，Agent 是运行时动态决策
- Agent 循环 = 思考 → 选工具 → 执行 → 观察 → 再思考，直到给出答案或触顶
- Tool 三要素：名称、描述、参数 schema，其中描述质量决定选择准确率
- 模型只负责"决定调用"，框架负责"实际执行"
- function calling 的本质是模型输出结构化调用意图，不是模型真的执行了代码
- 工具不是越多越好，超过 10 个选错率明显上升
- 必须设 max_iterations，工具报错要友好返回
