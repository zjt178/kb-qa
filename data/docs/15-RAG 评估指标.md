# 15 RAG 评估指标

## 概述

RAG 系统最常遇到的困境是：改完一个参数，感觉"好像好一点了"，但说不清到底好在哪里、好了多少。解决这个问题的唯一办法是**固定测试集 + 分层指标**。本文讲清三层指标分别测什么、怎么算，以及为什么没有测试集就没有优化。

## 为什么要分层评估

RAG 是一条链路：检索 → 拼上下文 → 生成。链路中任何一环出问题，最终答案都会错，但**错误的表现形式不同**：

- 检索没找到正确文档 → 生成层一定错（除非模型自己会）
- 检索找到了、但排在很后面 → 可能被截断在 TOP\_K 之外，同样等于没找到
- 检索没问题，但模型没照着参考内容答 → 生成层的问题

只看最终答案好坏，无法定位是哪一环的锅。所以要分层测：**检索层看"找得到吗、排得前吗"，生成层看"答得对吗、编了吗"，工程层看"快吗、贵吗"**。

## 检索层指标

**Hit\@K（命中率）**
前 K 条检索结果里，是否存在包含正确答案的文档块。有就是 1，没有就是 0，全部问题取平均。

- 最直观的指标，回答"系统能不能找到"
- K 通常取 3 或 5，与线上实际使用的 TOP\_K 一致
- 计算需要知道"哪一块才是正确的"，所以测试集里每题要标注 `keywords`——检索结果里出现该关键词就算命中

**MRR（Mean Reciprocal Rank，平均倒数排名）**
第一个正确结果的排名的倒数，取平均。

- 如果一个正确结果排在第 1 位，得分 1；排第 2 位，得分 0.5；排第 3 位，得分 0.33
- 它衡量"排得够不够前"。Hit\@5 都是 1 的两个系统，MRR 可能相差很多——一个把答案放第 1 位，另一个放第 5 位
- MRR 对位置敏感，是排序质量的核心读数

**Recall\@K / Precision\@K（召回率 / 准确率）**

- 召回率：所有正确文档块里，有多少被前 K 条覆盖
- 准确率：前 K 条里有多少是相关的
- 语料量大、一题对应多个正确块时更常用。小规模知识库用 Hit\@K + MRR 就够了

## 生成层指标

**忠实度（faithfulness）**
答案是否完全由检索内容支撑。用 LLM-as-judge 打分量化：

```
prompt: 请根据参考内容给下面这个答案的忠实度打分（1-5）
5 = 每一句都能在参考内容里找到依据
1 = 答案内容参考里基本没有
```

这是防幻觉的核心指标。**注意：拒答题不应该计入忠实度统计**——拒答的答案本来就不基于检索内容，把它算进去会把平均值拉低，得到误导性的结论。

**答案相关性（answer relevancy）**
答案是否真的在回答问题，而不是答非所问或绕圈。检索对了但模型答偏了，这个指标会掉。

**拒答准确率**
标记为 `must_refuse` 的问题里，真正被正确拒答的比例。这条是**幻觉防线的直接读数**，也是面试时最容易讲出故事的一项——"我构造了 5 道知识库里没有的题，拒答率从 40% 提到 100%"。

## 工程层指标

- **平均延迟**：一次问答从请求到返回的耗时，通常按毫秒计
- **P95 延迟**：95% 的请求在多少毫秒内完成，反映长尾表现。平均值好但 P95 差，说明有部分请求极慢
- **首 token 延迟**：流式输出场景下更关键的指标，用户感知到的"响应速度"其实是它
- **单次成本**：调用 API 时按 token 计费，本地模型则体现为算力占用

延迟指标的读法有个坑：**第一次查询会包含模型冷启动**，往往比其他请求慢好几倍。看指标应该看平均值，或者先跑一次预热。

## 测试集是前提

指标是算在**固定题集**上的。没有测试集，改完参数只能"感觉变好了"，无法量化、无法对比。

一个可用的测试集规格：

- **20-30 条问题**，覆盖语料的主要主题
- 每题的字段：
  - `question`：问题本身（必填）
  - `keywords`：命中判定依据，出现即算检索命中。选**专有名词、术语、数字**这类"一出现就说明找对了"的词，不要选"系统""方法"这种到处都是的词
  - `ground_truth`：标准答案，用于忠实度打分（可选）
  - `must_refuse`：标记该题应该被拒答（用于拒答率）
- 配比建议：15 条带 keywords（其中一半带 ground\_truth），3-5 条 must\_refuse

关键纪律：**测试集一旦定下来，优化过程中不要改**。改了就没法对比前后。要扩充就整批扩充，然后所有模式重跑一遍。

## 评估工具

- **RAGAS**：业界标准库，内置忠实度、答案相关性、上下文精度等指标，开箱即用，但依赖较重
- **自建轻量脚本**：自己写几十行，实现 Hit\@K / MRR / 忠实度 / 拒答率。依赖少、逻辑透明、便于按自己语料定制

两者没有优劣：RAGAS 适合快速拿到业界认可的指标，自建脚本适合完全掌控计算逻辑。**面试时被问到"指标怎么算的"，能讲出自建脚本的实现细节，比说"我用了 RAGAS"更有说服力。**

## 要点清单

- 分层评估：检索层（找得到吗）、生成层（答得对吗、编了吗）、工程层（快吗、贵吗）
- Hit\@K 看能不能找到，MRR 看排得够不够前
- 忠实度用 LLM-as-judge 量化，拒答题不计入统计
- 拒答准确率是幻觉防线的直接读数
- 延迟看平均值和 P95，第一查询含冷启动不可用
- 测试集固定不动，改参数后所有模式重跑才有对比意义
- 指标必须有 before/after 对比，否则没有意义
