# 向量数据库选型对比

## 概述

向量数据库负责存储高维向量并支持近邻查询。选型时要在部署成本、过滤能力、扩展性和运维复杂度之间权衡。本文对比几类常见方案的能力边界。

## 专用向量数据库

专用向量库为向量检索从头设计，通常内置多种索引结构、分片和副本机制，支持水平扩展。

优点是开箱即用、性能可控；代价是引入新的组件，需要额外的部署、监控和备份方案。团队如果没有专职运维，这类组件的长期成本容易被低估。

## 关系数据库的向量扩展

在已有的关系数据库上加装向量类型和近邻索引，最大的好处是不引入新组件，向量和业务数据可以在同一个事务里读写，过滤条件也能直接复用 SQL 的成熟能力。

代价是索引类型的选择少，超大规模下的性能上限低于专用方案。对于数据量在百万级以内、且已有关系数据库的项目，这通常是最省心的选择。

## 内存索引库

把向量索引加载到进程内存，随应用一起启动，没有独立服务、没有网络往返，开发和调试成本最低。

限制也很明显：索引是单机的，多副本要靠应用层自己解决；数据量受内存约束；不适合多写入者的并发场景。它适合原型验证和中小规模的知识库。

## 选型要问的问题

1. 数据量级和增长预期是多少
2. 是否需要按业务字段做过滤，过滤和向量检索能否在同一层完成
3. 是否要求高可用和多副本
4. 团队能否承担一个常驻服务的运维成本
5. 是否需要频繁更新和删除，还是以离线批量写入为主

把这些问题答清楚，选型基本就定了，不必纠结基准测试的排名。

## 要点清单

- 专用向量库能力强，但增加组件与运维成本
- 关系库扩展不动架构，过滤与事务能力可复用，适合百万级以内
- 内存索引零部署成本，但单机、受内存限制
- 选型先问数据量、过滤需求、高可用要求
- 频繁增删改的场景要重点确认索引更新的开销
