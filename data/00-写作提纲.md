## 06 嵌入模型原理与常见模型

**核心问题**：一句话是怎么变成一串数字的？为什么相似的句子向量也相似？

- **概述**：嵌入 = 把文本映射到高维向量空间，语义相近的文本在空间里距离也近
- **从词袋到神经网络**：早期 one-hot / TF-IDF 只能表示"词出现过"，无法表示语义；神经网络嵌入能捕捉上下文
- **双塔结构（bi-encoder）**：问题和文档分别过同一个模型，各自出一个向量，靠向量距离算相似度。**这是检索阶段用的结构**，优点是文档向量可以提前算好、建索引
- **为什么它能表达语义**：训练目标是让"意思相近的句子"向量靠近、"无关句子"推远（对比学习、正负样本对）
- **常见中文嵌入模型选型**：
  - bge-small-zh-v1.5：小、快，25MB，适合 demo 和本地跑
  - bge-m3：中大，支持多语言，支持长文本（8192 token），检索效果好
  - bge-large-zh：更大更准，但慢、吃显存
  - text-embedding-3（OpenAI）：效果稳但要调 API、要花钱
- **选型权衡**：效果 vs 速度 vs 部署成本；本地项目优先考虑 ollama 能拉的模型
- **要点清单**：嵌入是语义映射不是关键词匹配 / 检索用双塔结构 / 文档向量可预计算 / bge 系列是中文主流 / 模型越大越准也越慢

## 07 向量维度与归一化

**核心问题**：向量里的每一维代表什么？为什么换了模型索引必须重建？

- **概述**：向量是一串浮点数，维度就是数字的个数（bge-small 是 512 维，bge-m3 是 1024 维）
- **维度不是"可解释的特征"**：每一维没有人类可读的含义，是整个模型协同训练出来的分布式表示，不要试图解释"第 37 维代表什么"
- **维度高低的影响**：维度高表达能力更强，但存储和计算成本也高；小模型维度低，效果可能稍弱
- **归一化（normalize）**：把向量长度缩放到 1。归一化后，余弦相似度和内积是等价的，很多检索库默认要求归一化
- **为什么换嵌入模型必须重建索引**（重点，面试常问）：
  1. 维度可能变（512 → 1024），新旧向量根本没法比
  2. 即使维度一样，语义空间也不同——两个模型各说各的"方言"，旧向量在新空间里是随机噪声
  3. 结论：换模型 = 全量重建，不能只换配置
- **要点清单**：维度 = 数字个数 / 每一维不可解释 / 归一化后余弦 ≡ 内积 / 换模型必须重建索引 / 重建时要 --force

## 08 相似度度量：余弦、内积、欧氏距离

**核心问题**：怎么衡量两个向量"像不像"？

- **概述**：三种主流度量，选哪个取决于向量是否归一化、关注方向还是距离
- **余弦相似度**：看两个向量的夹角，对向量长度不敏感。取值 -1 到 1，越接近 1 越相似。**文本检索最常用**
- **内积（点积）**：各维相乘再相加。值越大越相似。向量归一化后，内积 ≡ 余弦相似度（这就是很多库直接归一化+内积的原因，算得更快）
- **欧氏距离**：两点之间的直线距离，值越小越相似。关注绝对位置差异，常用于图像、音频
- **为什么文本多用余弦**：文本长度差异大（一句话 vs 一段话），余弦只关心"方向"（语义方向），不受长度干扰
- **工程实践**：FAISS 常用 IndexFlatL2（欧氏）或 IndexFlatIP（内积）；用内积时记得先把向量归一化
- **要点清单**：余弦看夹角、内积看累加、欧氏看距离 / 文本检索首选余弦 / 归一化后内积 ≡ 余弦 / 长度差异大的文本要靠余弦降干扰

## 09 纯向量检索的局限

**核心问题**：为什么光有向量检索还不够？——**这是混合检索的动机，必须写透**

- **概述**：向量检索擅长语义模糊匹配，但对精确匹配无能为力，有三类典型失败场景
- **场景一：专有名词、型号、缩写**。向量是语义压缩，低频词（BGE-M3、HNSW、RRF）在训练语料里出现少，向量质量差。搜"BGE-M3"可能匹配到泛泛讲"嵌入模型"的段落
- **场景二：数字与版本号**。搜"2027 年"和"2026 年"在向量空间里几乎无法区分，因为语义几乎一样
- **场景三：长尾关键词 / 精确短语**。想找"必须原样出现在文中"的字符串时，向量帮不上忙
- **本质原因**：向量检索求的是"意思近似"，不是"字面命中"——这是设计目标，不是 bug
- **补充局限**：跨语言、领域术语（模型没见过该领域语料）、否定句（"不包含 X" 和 "包含 X" 向量很近）
- **要点清单**：向量不等于精确匹配 / 专有名词、数字、长尾词是三大盲区 / 否定句也是坑 / 这就是要引入 BM25 的原因

## 10 BM25 关键词检索原理

**核心问题**：BM25 凭什么能补上向量的盲区？

- **概述**：BM25 是经典的关键词相关性打分算法，本质是"词频 + 逆文档频率"的改良版，靠字面匹配
- **TF（词频）**：某个词在文档里出现越多，越相关。但**有饱和**——出现 10 次和 100 次的差别远小于 1 次和 10 次（避免关键词堆砌刷分）
- **IDF（逆文档频率）**：一个词在越少文档里出现，它的区分度越高、权重越大。"的""是"几乎没权重，"HNSW"权重很高
- **文档长度归一化**：长文档天然更容易命中词，BM25 会做惩罚，让长短文档可比
- **k1 和 b 两个参数**：k1 控制词频饱和速度（常用 1.2-2.0），b 控制长度归一化强度（常用 0.75）
- **中文的问题**：BM25 按"词"统计，中文没空格，所以**必须先分词**（jieba）。分词质量直接决定 BM25 效果——"向量数据库"切成"向量/数据库"还是"向量数据库"会带来不同结果
- **与向量检索的互补**：BM25 命中字面、向量命中语义，两者天然互补，这是混合检索的理论基础
- **要点清单**：BM25 = TF × IDF + 饱和 + 长度归一化 / 靠字面匹配 / 中文必须先分词 / 专有名词是它的强项 / 与向量互补

## 11 混合检索与 RRF 融合

**核心问题**：两路检索各有各的分数，怎么合并成一个排序？

- **概述**：混合检索 = 同时跑向量检索和 BM25，再把两个结果列表融合成一个
- **为什么不能直接加权求和**：向量相似度（0-1）和 BM25 分数（可能 0-30）**量纲完全不同**，直接相加等于让 BM25 主导；而且两者分数分布不稳定，调权重很脆
- **RRF（Reciprocal Rank Fusion）的做法**：不看分数，只看**排名**。每个文档的得分 = Σ 1/(k + rank)，k 是平滑常数（常用 60）
  - 例：某文档在向量检索里排第 1、BM25 里排第 3 → 1/(60+1) + 1/(60+3) = 0.0322
- **RRF 为什么好用**：只用排名不用分数，天然免疫量纲问题；两路都排得靠前的文档自动得分最高；**几乎不需要调参**（k 值很鲁棒）
- **k=60 的作用**：避免第一名权重过大（如果 k=0，第一名得 1 分，第二名 0.5，差距过猛）；k 越大，各名次差距越平缓
- **实现要点**：两路各召回 N 条（通常 N > 最终要的 K，比如各取 20 条），融合后取前 K
- **要点清单**：混合 = 向量 + BM25 / 不能用加权求和（量纲不同）/ RRF 只用排名 / 公式 Σ1/(k+rank)，k 常取 60 / 两路先多召回再融合

## 12 重排序 Rerank

**核心问题**：为什么召回之后还要再排一次？

- **概述**：检索分两阶段——\*\*召回（recall）\*\*要快要全，\*\*重排（rerank）\*\*要准
- **双塔的瓶颈**：检索阶段的 bi-encoder 里，问题和文档**从不互相看见**（各自独立编码），所以只能算粗略的向量距离，精度有限
- **cross-encoder 的做法**：把「问题 + 文档」拼成一个输入，一起喂给模型，让模型在内部做完整的注意力交互，直接输出一个相关性分数。**精度高得多**
- **代价**：每个候选都要过一次模型，无法预计算，慢。所以只对召回的少量候选（如 20 条）重排，而不是对全库
- **典型流程**：向量/BM25 召回 20 条 → cross-encoder 逐条打分 → 重排取前 5 → 交给大模型
- **常用模型**：bge-reranker-base / bge-reranker-large；也可用 Cohere Rerank 等 API
- **何时值得上**：语料量大、对准确率敏感、且能接受额外延迟（几十到几百毫秒）
- **要点清单**：召回求全、重排求准 / 双塔不交互所以粗 / cross-encoder 拼接交互所以准但慢 / 只对少量候选重排 / 重排能明显提升 MRR

## 13 提示词工程与系统提示词设计

**核心问题**：怎么让大模型"老实"地用检索内容回答？

- **概述**：系统提示词是防幻觉的第一道闸门。RAG 的提示词不是"写个好看的人设"，而是写**规则**
- **三分法**：人设（你是谁）+ 规则（能做什么、不能做什么）+ 输出格式（怎么答）
- **RAG 提示词的必备规则**：
  1. 只根据参考内容回答，不许用你自己的知识补充
  2. 必须标注引用编号 \[n]
  3. 参考内容里找不到答案时，明确说"没有找到"，不许编
  4. 控制在合理长度（如 300 字内），避免啰嗦
- **为什么"必须拒答"这条最重要**：模型默认倾向是"无论如何都要给个答案"，这条规则是唯一能压制这种倾向的指令
- **举例说明技巧**：给一两个"正确回答"和"正确拒答"的范例，比只写规则更有效（few-shot）
- **temperature 的配合**：知识库问答要确定性，temperature 调到 0-0.2；调高会开始自由发挥
- **反面案例**：只说"你是一个专业的助手"而不写规则，模型会把检索内容当参考而非依据，照样编造
- **要点清单**：人设 + 规则 + 格式三分法 / 规则比人设重要 / "必须拒答"是防幻觉关键 / few-shot 示例更有效 / 知识库问答用低温

## 14 大模型幻觉：成因与检测

**核心问题**：幻觉从哪来？怎么知道自己的系统有没有幻觉？

- **概述**：幻觉 = 模型生成了流畅但不符合事实的内容，而且它自己"不觉得"在编
- **成因**：
  1. 模型的本质是"预测下一个 token"，流畅性优先于真实性
  2. 训练数据里没有的知识，模型会基于统计规律"合理推测"
  3. 用户问题本身诱导（"请说说 XX 的缺点"，即使 XX 没缺点）
  4. 上下文里没有答案时，模型倾向于"补全"而不是承认不知道
- **RAG 里幻觉的两种形态**：一是答案编造了知识库里没有的内容（越出参考）；二是答案正确但引用了错误的来源（引用错配）
- **检测方法**：
  - **LLM-as-judge**：拿另一个模型当裁判，给"答案是否完全基于参考内容"打 1-5 分（我们项目里用的就是这个）
  - **引用核对**：检查答案里的 \[n] 标注和实际引用内容是否对得上
  - **拒答测试**：构造知识库里肯定没有的问题，看模型是拒答还是硬答
- **缓解手段**：强化系统提示词的规则、降低 temperature、要求强制引用、检索质量本身要提高（检索错了，生成一定错）
- **要点清单**：幻觉来自语言模型的本质倾向 / 分为"编内容"和"引错源"两类 / LLM-as-judge 可量化 / 拒答测试是必需的验收项 / 检索质量是幻觉的地基

***

## 15 RAG 评估指标

**核心问题**：怎么证明你的系统"变好了"？——**简历数字的理论依据**

- **概述**：RAG 评估要分层看——检索层、生成层、工程层，只看一个维度会得出错误结论
- **检索层指标**：
  - **Hit\@K**：前 K 条结果里有没有命中正确的文档块。最直观，衡量"找得到吗"
  - **MRR（平均倒数排名）**：第一个正确结果排在第几位，取倒数再平均。衡量"排得够不够前"
  - **Recall\@K / Precision\@K**：召回率与准确率，语料量大时更常用
- **生成层指标**：
  - **忠实度（faithfulness）**：答案是否完全基于检索内容，用 LLM 打分量化
  - **答案相关性（answer relevancy）**：答案是否真的回答了问题（而不是答非所问）
  - **拒答准确率**：该拒答的问题真的拒答了吗——防幻觉的硬指标
- **工程层指标**：平均延迟、P95 延迟、单次成本
- **为什么必须有测试集**：指标是算在固定题集上的。没有 20-30 条固定问题，改动完只能"感觉变好了"，无法量化，也无法写进简历
- **评估工具**：RAGAS（业界标准库）、自建轻量脚本（我们项目的做法，依赖少、可控）
- **要点清单**：分层评估（检索/生成/工程）/ Hit\@K 和 MRR 看检索 / 忠实度和拒答率看生成 / 测试集是前提 / 指标必须有 before/after 对比才有意义

## 16 LCEL 与 Runnable

**核心问题**：`prompt | llm | parser` 这个管道符凭什么能串起来？

- **概述**：LCEL（LangChain Expression Language）是 LangChain 的组合语法，核心是一套统一的 Runnable 接口
- **管道符的机制**：Python 里 `a | b` 实际调用 `a.__or__(b)`。LangChain 的所有组件都实现了 `__or__`，返回一个 `RunnableSequence` 对象，把执行顺序记录成一条流水线
- **它不是什么**：不是按位或运算，也不是语法糖——它是运算符重载
- **数据流**：`chain.invoke({...})` 时，dict → prompt 填模板产出提示词 → llm 调用模型产出 AIMessage → parser 抽出纯文本。每一环只认上一环的输出格式
- **Runnable 带来的能力**：因为组件统一，整条链免费获得 `invoke()`（单次）、`batch()`（批量）、`stream()`（流式）、`ainvoke()`（异步）——不用改代码
- **为什么取代了老的 LLMChain**：老式 Chain 是黑盒、不统一；LCEL 让每个组件都是 Runnable，可以任意组合、嵌套、复用
- **验证方法**：`print(type(chain))` 会打印 `RunnableSequence`——课上的名词落到真实类上
- **要点清单**：LCEL 是组合语法 / 靠 `__or__` 运算符重载 / 返回 RunnableSequence / 每环只认上环输出 / 免费获得 stream/batch/异步

## 17 LangChain Agent 与 Tool 调用机制

**核心问题**：Agent 和 Chain 有什么本质区别？

- **概述**：Chain 是**固定流程**（你写死了先检索再生成）；Agent 是**动态决策**（由模型决定下一步做什么）
- **Agent 的核心循环**：思考 → 选择工具 → 执行 → 观察结果 → 再思考，直到得出答案或达到步数上限
- **Tool 的三要素**：名称（模型靠它选工具）、描述（模型靠它判断什么时候用——**描述写得越清楚，选得越准**）、参数 schema（模型靠它构造调用参数）
- **工具调用的底层机制**：现代模型支持 function calling / tool calling，模型输出的不是文本而是结构化的"要调用哪个工具、参数是什么"；框架执行工具后把结果作为新消息塞回对话，模型继续
- **描述为什么关键**：模型选工具完全靠读描述。描述含糊（"查询数据"）会导致选错；描述具体（"根据订单号查询订单状态，参数是 12 位订单号字符串"）才准
- **常见 Agent 模式**：ReAct（思考-行动交替）、Plan-and-Execute（先规划再执行）、多 Agent 协作
- **注意事项**：工具多了会选错、循环可能不收敛（要设 max\_iterations）、每次工具调用都是额外延迟和成本
- **要点清单**：Chain 固定流程、Agent 动态决策 / 循环是思考-行动-观察 / 三要素：名称、描述、参数 / 描述质量决定选择准确率 / 工具调用靠结构化输出实现

***

## 18 MCP 协议与在 LangChain 中的使用

**核心问题**：MCP 想解决什么问题？为什么它值得学？

- **概述**：MCP（Model Context Protocol）是标准化协议，让大模型应用能以统一方式连接外部工具和数据源
- **它解决的问题**：在 MCP 之前，每个应用对接每个工具都要写一套适配代码（N 个应用 × M 个工具 = N×M 份代码）。MCP 把接口标准化，变成 N+M
- **架构与层级**：
  - **Host（宿主）**：跑大模型的应用，如 Claude Desktop、你自己的 Agent 程序
  - **Client（客户端）**：Host 内部负责和 Server 通信的连接器，一个 Server 对应一个 Client
  - **Server（服务端）**：暴露能力的程序，把工具、资源、提示词包装好对外提供
  - 三者关系：1 个 Host 可以连多个 Server（各自一个 Client）
- **Server 暴露的三类能力**：Tools（可调用的函数）、Resources（可读的数据，如文件内容）、Prompts（预置的提示词模板）
- **传输方式**：本地用 stdio（标准输入输出，进程间通信），远程用 HTTP/SSE
- **在 LangChain 里使用**：`langchain-mcp-adapters` 包把 MCP Server 的工具转成 LangChain 的 Tool，直接塞进 Agent 就能用——**这是它和前面 17 篇的接口**
- **为什么值得学**：2025 年后才普及的新协议，会的人少；写进简历有差异化；面试聊 Agent 生态时是加分项
