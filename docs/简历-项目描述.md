## 一、简历项目栏（直接复制）

### 精简版（3 行，适合简历空间紧张）

> **企业知识库问答系统（RAG 全链路）** · 个人项目 · Python / LangChain / FAISS / Ollama / FastAPI
> - 独立实现完整 RAG 链路：40 篇中文语料入库（加载清洗 → 500/80 切分 → bge 嵌入 → FAISS 索引）→ 混合检索 → LLM 生成带 `[1][2]` 引用溯源的答案 → FastAPI 服务 + 中文 Web UI。
> - 自建 29 题评测集与评估脚本，量化 Hit@K / MRR / 严格证据覆盖率 / LLM 忠实度 / 拒答准确率 / 延迟六项指标；对比向量检索、BM25 混合检索（RRF, k=60）、cross-encoder 精排三条策略。
> - **混合检索把严格证据覆盖率从 85.7% 提到 90.5%**（关键词覆盖率 90.5% → 95.2%，忠实度持平）；**发现并归因精排在该规模下的负优化**（覆盖率降至 81.0%、延迟增至 3.2 倍），定位为 pointwise 判据拆散多证据问题的证据块。

### 展开版（面试时口头讲的骨架）

**技术栈**：LangChain（LCEL）、FAISS、BM25(rank-bm25 + jieba)、bge-small-zh-v1.5（512 维）、bge-reranker-base、qwen2.5-coder、FastAPI、Ollama。

**关键工程决策**
1. **检索融合用 RRF 而非加权求和**——BM25 分数无上界、余弦相似度在 [-1,1]，量纲不同不能直接相加；两者分布随语料漂移，权重标定不出来。RRF 只用名次算 `1/(k+rank)`，对量纲和异常值免疫。
2. **索引重建做成"先建后删"**——原实现先 `rmtree` 旧索引再嵌入建新索引，而嵌入依赖 Ollama，服务一挂就变成"旧的没了新的也没建成"。改成在临时目录建好、成功后才替换。
3. **评测口径严格化**——发现宽松 Hit@K 在三种模式下双双封顶 1.0，没有区分度；补充"前 5 条覆盖全部关键词"的严格口径和平均关键词覆盖率，指标才重新有分辨力。
4. **可复现性**——每次评估结构化写入 `history.jsonl`，报告落盘为 `report-<mode>.md`，早期被推翻的版本存档在 `eval/archive/`。

## 三、面试官会追问什么（含答题要点）

### Q1. 只有 40 篇语料、122 块，这个规模的结论有意义吗？

有，但要说清边界。它的意义不是"证明 hybrid 更好"，而是**建立了一套能证伪的评估方法**，并且诚实地报出了天花板：18/21 题三模式一致，说明增量只在少数查询类型上。小规模的结论不能外推到大库，但**方法可以**——换语料、换规模，同一套脚本重跑即可。

### Q2. Hit@K 都已经 1.0（甚至 95%+）了，还谈什么提升？

正因为宽松 Hit@K 在三种模式下都封顶，才说明这个指标失效了。我补了两个更严的口径：
- **Hit@K(全词)**：前 5 条必须覆盖**全部**关键词才算命中。它衡量的是"证据是否齐全"，直接对应下游能不能答全。
- **关键词覆盖率**：平均命中几成，能反映部分命中。

指标一旦没有区分度，就说明**它测的不是你想优化的东西**，要换指标，而不是换个说法。

### Q3. 为什么用 RRF，不用加权求和 / 归一化后再线性融合？

三个理由：
1. **量纲不同**：BM25 分数无上界（随语料和文档长度漂移），余弦相似度在 [-1,1]，直接加权没有物理意义。
2. **归一化不稳定**：min-max 归一化依赖当前返回集合的极值，多召回一条就可能整体挪位；z-score 需要稳定的分布假设，两路分布随查询类型变化。
3. **RRF 只吃名次**：`score = Σ 1/(k + rank_i)`，k 取论文推荐值 60 起平滑作用——k 越大越"拉平"头部差异，防止某一路靠自己排得靠前就一票定音。代价是丢掉了"分数差多少"的信息，但在两路异质检索器融合的场景下，这个代价值得。

### Q4. 精排（cross-encoder）理论上更强，为什么你的实验里反而更差？换个模型能救吗？

**换模型救不了**，因为问题在判据粒度，不在模型质量。

- 召回阶段（向量 / BM25）判的是"这块和问题像不像"，RRF 只问"两路是否都认可"——多证据题的两块证据都能进前五。
- cross-encoder 把「问题 + **单个**块」拼起来打分，本质在问"**这一块自己能不能把问题答完**"。只含半份答案的块就被判低相关，直接踢出前五。

所以精排越准，"拆散证据"越彻底。#29 就是活例子：vector 覆盖 1/2 → hybrid 2/2（两块齐全且排第 1）→ rerank **0/2**（全被踢出）。两次独立运行均在同一题、同一位置复现。

真要救有三条路：① 问题侧改造，把多跳问题拆成一跳一问；② 换 **listwise** 重排（一次看多块再排序）或先做证据聚合再精排，别用 pointwise；③ **按查询类型路由**，字面术语型查询开精排、语义型不开关。

### Q5. 忠实度怎么测的？LLM-as-judge 可信吗？

用同一个本地 7B 模型当裁判，1-5 分五档定义（5 = 完全基于资料且有引用，1 = 基本是编造）。**可信度有限**：裁判与被评模型同源、存在位置与长度偏差。所以我的用法有边界：

1. 只做**模式间横向对比**，不下"绝对质量"结论；
2. 报告里同时输出有效样本数 `faithfulness_n`——**分母不齐时绝不比较均值**；
3. 这一条是被坑出来的：评审要求"只输出一个数字"，模型却回「【答案】完全基于【参考资料】。」，正则匹配不到就被静默丢弃，两次运行丢的不是同一批题，分母从 22 变到 24，出现"hybrid 拖低忠实度"的假象；修好后两模式都是 4.29，完全持平。

后续可换更强模型 / 多裁判投票 / 换 RAGAS 的指标化打分。

### Q6. 拒答是怎么实现的？怎么保证该拒的真的拒了？

两层：
1. **提示词围栏**——系统提示词明确"若参考资料不足以回答，必须回复固定拒答话术，不得使用外部知识"；
2. **评测**——5 道 `must_refuse` 题，检测答案是否命中拒答话术，拒答准确率实测 1.0。

这一项比"答对多少"更能说明系统是否可用：企业场景里，**编造答案比拒答危险得多**。

### Q7. 换个嵌入模型为什么要重建整个索引？

两个原因：
1. **维度可能不同**——bge-small-zh 是 512 维、bge-m3 是 1024 维，FAISS 索引结构对不上，直接加载会报错。
2. **更根本的是语义空间不同**——同一句话在两个模型下的向量坐标没有可比性。如果只重建 query 侧、沿用旧文档向量，余弦相似度算出来的是噪声。所以必须 `ingest.py --force` 全量重embed。

### Q8. 怎么保证生成的答案没有幻觉？

三道防线：**检索给证据 → 提示词约束只能在证据内作答 → 引用溯源可核对**。答案里带 `[1][2]` 指向具体原文块，用户能自己验。再加上评估里的忠实度和拒答率两个指标兜底。

### Q9. 这个项目里你印象最深的问题？

"下载成功"不等于"能用"。重排模型 1.06GB 下载显示成功，一加载报 `config.json is not a valid JSON file`——查下来是 **Windows 无管理员权限时建不了符号链接**，HF 缓存的 `snapshots/` 目录靠软链指向 `blobs/`，软链建不起来就只剩 0 字节空壳，而 `blobs/` 里的权重其实完好。最后按文件头把哈希命名的 blob 认出来手工改名复制解决，`config.py` 也顺势支持了本地模型目录。

教训落成一句话：**装完模型必须真的加载一次跑个 predict，"下载完成"不是验收线。**

### Q10. 如果语料从 122 块涨到 10 万块，方案怎么改？

1. **向量库**：FAISS → Milvus / pgvector，上 HNSW 或 IVF-PQ 索引，FAISS 单机内存索引撑不住。
2. **分块策略重做**：固定 500 字切分会让块数爆炸且语义割裂，改父子分块（子块检索、父块入 prompt）或语义分块。
3. **检索加过滤**：元数据预过滤（按文档类型 / 时间 / 租户）先缩小候选，再做向量检索。
4. **精排重新变成正收益**：候选池大、噪声多，pointwise 精排的价值才显现——**同一技术在不同规模下结论相反**，这正是我这个项目量出来的那个边界。
5. **查询侧优化**：查询改写 / HyDE / 多查询扩展，小库上做这个没意义，大库上收益明显。
6. **评估改造**：10 万块不可能全量 LLM judge，改分层抽样 + 离线指标为主、生成质量抽样。
